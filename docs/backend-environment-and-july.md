# Unified backend environment and account maintenance

`config.settings` now loads `.env` and `.env.local` for every Django entry point, including direct management commands. The local file overrides the base file. Explicit process variables retain priority for migrations and hosted tests. The Windows launcher already loads both files, so interactive `changepassword` and ASGI no longer silently select different default databases in a fresh shell.

The task-specific `repair_july_database.cmd` runs the paired Python script with UTF-8 enabled. With the backend stopped, it selects the launcher's database, validates that `fuck` exists, obtains a new `july` password interactively and backs up all records before deleting the old `july`. A privileged account named `july` is refused. It recreates `july`, adds mutual friendship and sets the two companion records to 39,840 seconds. The new account's watched total is 54,000 seconds. Other accounts and `fuck`'s password are preserved; deleting the original `july` also deletes its dependent records through Django's normal cascades.

The requested visible genre values are 63, 10, 9, 9 and 3 percent. The unspecified remainder is stored as `__unclassified__` and included in the denominator without being emitted as a visible genre. This preserves the supplied percentages instead of normalizing 94 to 100. No dated activity or longest-session value is invented.

The deployed repair installs the small environment module and surgically updates settings/activity serialization, backing up the originals. It consolidates DATABASE_URL into `.env`. Inactive SQLite files matching the known backend filenames in the deployment root are zipped, verified and removed from that root. It never deletes the selected SQLite or drops unknown PostgreSQL databases. Backups remain in `_database_backups`.

Validation: three configuration-loader unit tests pass. An isolated SQLite deployment test passes migration, account recreation, fresh-shell authentication, exact API percentages, mutual companion totals, preservation of other users, backup creation and inactive SQLite removal. The Windows test deployment omits the Daphne application registration to avoid starting a reactor during these database-only checks. Actual production PostgreSQL access and changes require running the repair in the user's server folder; that folder is not mounted in this workspace.
